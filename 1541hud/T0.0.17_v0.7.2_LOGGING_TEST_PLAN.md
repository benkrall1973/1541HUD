# 1541HUD T0.0.17 - OneROM v0.7.2 Native Logging Experiment

## Goal

Prove that the 1541HUD UB4 user plugin can write application data through OneROM v0.7.2's native log-channel API and have the stock v0.7.2 USB log drain forward it to the PC, without changing the hardware-proven passive monitor implementation.

This is intentionally a transport-only experiment. It does **not** replace the existing 1541HUD mailbox/CDC telemetry yet.

## Baseline

- Development base: GitHub `dev-1541hud`
- Base commit: `8a407804b14bbfe2f9dea060fc57ceb44a62d447`
- OneROM firmware: v0.7.2
- Hardware-proven monitor implementation remains `1541hud_probe_t016_v072_baseline.c`
- UB4 remains passive.
- Existing UB4 wiring remains unchanged:
  - 6502 R/W -> GPIO9
  - PHI2 -> GPIO8
  - UC2 /CS2 -> GPIO25
  - UC2 PB7/SYNC -> GPIO24

## What T0.0.17 changes

A thin wrapper source, `1541hud_probe_t017_v072_logging.c`, is added around the unchanged T0.0.16 implementation.

The wrapper:

1. Defines plugin version `0.0.17.0` with minimum OneROM firmware `0.7.2`.
2. Looks up `ORA_ID_LOG_OPEN_WRITE` and `ORA_ID_LOG_WRITE`.
3. Claims OneROM log channel 0 for the 1541HUD user plugin.
4. Writes exactly one application-log startup record:

   `1541HUD T0.0.17 v0.7.2 native LOG_WRITE startup test`

5. Permanently transfers execution into the unmodified T0.0.16 monitor implementation.

If the native logging API cannot be looked up or the channel cannot be claimed, the wrapper uses OneROM's error log to report the failure before continuing into T0.0.16. A logging failure therefore must not prevent the monitor from running.

## What T0.0.17 deliberately does not change

- PIO instructions or sample timing
- DMA channel 11 setup
- bus GPIO input-only safety check
- UC2 `/CS2` decode
- GPIO24 SYNC input
- track and half-track logic
- HOME logic
- motor / head IN / OUT / STALL / PARK behavior
- write-protect logic
- density D0-D3
- HDRPHY / sector decoding
- RPM
- SYNC counting
- mailbox format
- existing USB CDC telemetry formatting
- GUI protocol
- UB4 passive-serving protection in `pio.c`

Existing `STATE` and `SYNC` lines intentionally retain the `T0.0.16` text for this experiment. That is a feature, not an omission: it proves the proven baseline code was not edited merely to make the version string prettier.

## Why channel 0 is correct

OneROM v0.7.2 defines channel 0 as its log channel. Its USB system plugin claims channel 0 **for reading** and drains that data to CDC while a terminal is attached. Read and write claims are independent. The 1541HUD T0.0.17 wrapper claims channel 0 **for writing**, while OneROM's own firmware log may still be interleaved on that channel.

The v0.7.2 write API is non-blocking. A record is either stored whole or dropped whole with `ORA_RESULT_LOG_FULL`; it never stalls waiting for USB. This is desirable for a passive timing-sensitive monitor.

## Build

Builder:

`1541hud/Build-1541HUD-T017-v072-Logging.ps1`

Expected output names:

- `1541HUD_OneROM_T0.0.17_v0.7.2_Logging.bin`
- `1541HUD_OneROM_T0.0.17_v0.7.2_Logging.uf2`

The build preserves copies of:

- T0.0.17 wrapper source
- T0.0.16 baseline dependency source
- v0.7.2 USB/1541HUD bridge source

A branch-only GitHub Actions workflow, `.github/workflows/1541hud-t017-build.yml`, independently compiles the passive base firmware, exact T0.0.17 user plugin, and USB system plugin before hardware is involved.

## Hardware test procedure

When a physical 1541/OneROM is available:

1. Build T0.0.17 from the synchronized branch.
2. Record SHA256 hashes of BIN, UF2, wrapper source, baseline dependency, and USB source.
3. Flash the T0.0.17 UF2 to the dedicated UB4 monitor OneROM only.
4. Power-cycle the 1541.
5. Confirm the drive boots normally and can read a directory.
6. Open the OneROM CDC port in PuTTY or another terminal.
7. Confirm the standard OneROM v0.7.2 USB log banner appears.
8. Confirm the new line appears:

   `1541HUD T0.0.17 v0.7.2 native LOG_WRITE startup test`

9. Confirm normal legacy telemetry still appears, including `STATE T0.0.16` and `SYNC T0.0.16`.
10. Run the existing T0.0.16-compatible GUI and verify the same basic monitor functions as the baseline: track, motor, head state, WP, density, RPM, sectors/HDRPHY and SYNC.

## Pass criteria

T0.0.17 passes only if all of the following are true:

- cloud build of the exact T0.0.17 plugin passes;
- 1541 boots and remains usable;
- new native `LOG_WRITE` startup record reaches the PC;
- existing T0.0.16 telemetry remains alive;
- no regression is observed in the passive monitor's core functions;
- no bus-driving or UB4-serving regression occurs.

## Failure handling

Do not overwrite or relabel T0.0.16. If T0.0.17 fails, preserve its source and build artifacts with the failure notes and revert the hardware to the known T0.0.16 UF2.

Do not merge this experiment into `dev-1541hud` merely because it compiles. Hardware proof is required first.

## Next step after a pass

A successful T0.0.17 proves OneROM-native outbound application logging can coexist with the existing 1541HUD transport. T0.0.18 can then compare one small piece of live 1541HUD telemetry over the native non-blocking log channel against the current mailbox/CDC path. Only after that comparison should any existing USB transport code be considered for removal.
