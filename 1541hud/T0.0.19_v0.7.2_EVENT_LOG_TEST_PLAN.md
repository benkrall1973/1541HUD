# 1541HUD T0.0.19 — v0.7.2 native event-log test

Temporary experiment based on the hardware-proven T0.0.18 branch. This is not a release.

## Change and safety boundary

T0.0.19 is an isolated copy of the T0.0.18 UB4 monitor source. PIO/DMA setup, passive-input checks, snapshot decode, mailbox, USB CDC formatting and GUI protocol are unchanged. Native application-log writes occur only after captured samples are drained, only when a decoded value changes, and never retry or wait if the OneROM log ring is full.

Expected native records:

- `1541HUD T0.0.19 EVENT MOTOR=0` or `=1`
- `1541HUD T0.0.19 EVENT TRACK=<n>` when DOS writes a new track value
- `1541HUD T0.0.19 EVENT HOME=ANCHORED` when the existing DOS-track-one home anchor is observed

The startup motor record establishes the initial cached state. This test intentionally does not change the legacy `STATE`, `SYNC`, `RPM`, `HDRPHY`, mailbox, or GUI identity; those continue to identify as T0.0.16/T0.0.17 by design.

## Build on the Windows test machine

Use branch `t0.0.19-v0.7.2-event-log` in `C:\1541HUD_LOCAL` after confirming the working tree is clean. Run `1541hud/Build-1541HUD-T019-v072-EventLog.ps1` with the same OneROM CLI, Arm toolchain and picotool configuration used for T0.0.18.

Expected image: `OneROM/build-1541hud/1541HUD_OneROM_T0.0.19_v0.7.2_EventLog.uf2`.

The branch workflow compiles the passive base firmware, exact T0.0.19 user plugin and preserved USB plugin; it does not produce a flashable UF2. Retain the builder's source copies and SHA256 hashes.

## Hardware test

1. Keep the T0.0.18 UF2 available for recovery. Flash the locally built T0.0.19 UF2 only to the dedicated UB4 monitor.
2. Power-cycle and read a disk directory. Confirm normal drive operation.
3. Open the CDC log. At idle, confirm one `EVENT MOTOR=0`. Run the track-cycle program and confirm changing `EVENT TRACK=<n>` records; use its home/knock action to confirm `EVENT HOME=ANCHORED`. Confirm motor transitions correlate with legacy `MOTOR state=0/1`.
4. Confirm the log is event-based: it must not repeat records once the state is unchanged.
5. Close the log client and run Reconnect Test 02. Verify normal GUI telemetry and a disconnect/reconnect recovery.
6. Stop and reflash T0.0.18 if drive behavior, capture telemetry, or LED state regresses.

Record hashes and observations before considering any merge into `dev-1541hud`.

## Hardware result — 2026-09-13

**PASS — expanded diagnostic-log checkpoint complete.** The dedicated UB4 test board booted and read normally. Native logging was bounded and correlated with the legacy monitor stream: motor transitions were reported as `EVENT MOTOR=0/1`; the track-cycle program reported valid `EVENT TRACK=18`, `25`, `35`, and `1`; and one `EVENT HOME=ANCHORED` was emitted when the valid track sequence returned to 1. Invalid raw values and repeated home records were excluded.

The existing Reconnect Test 02 GUI remained functional through the cycle: track, density, RPM, sector history, SYNC, motor and write-protect reporting were correct. Disconnect/reconnect resumed live telemetry normally. No capture overrun, queue overflow, drive lockup, or fault LED regression was observed.
