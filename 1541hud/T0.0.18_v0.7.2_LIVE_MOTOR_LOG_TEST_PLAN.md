# 1541HUD T0.0.18 — v0.7.2 native live-motor log test

Temporary experiment based on the hardware-tested T0.0.17 branch. This is not a release.

## Change and safety boundary

One isolated copy of the T0.0.16 UB4 monitor source is used for T0.0.18. PIO/DMA setup, passive-input checks, snapshot decode, mailbox, USB CDC formatting and GUI protocol are unchanged. After each DMA batch is drained, the user plugin attempts at most one nonblocking OneROM application-log write per second:

- `1541HUD T0.0.18 LIVE MOTOR=0`
- `1541HUD T0.0.18 LIVE MOTOR=1`

The sampled value is the same mailbox `last_motor` bit used by the existing `MOTOR state=` event. When the native log channel is unavailable or full, no retry or blocking wait is performed. Baseline `STATE`, `SYNC`, `RPM` and `HDRPHY` continue to say T0.0.16 by design. The GUI remains `1541HUD_T0.0.17_v0.7.2_Reconnect_Test_02.py`.

## Build on the Windows test machine

Use branch `t0.0.18-v0.7.2-live-motor-log` in `C:\1541HUD_LOCAL` only after confirming the working tree is clean. Run `1541hud/Build-1541HUD-T018-v072-LiveMotorLog.ps1` from PowerShell with the same OneROM CLI, Arm toolchain and picotool configuration used for T0.0.17. The script copies the exact T0.0.18 source, unchanged T0.0.16 dependency, and USB bridge into `OneROM/build-1541hud`, produces the BIN/UF2, and prints SHA256 hashes. Keep these source copies with the binaries. Do not rename or overwrite the T0.0.17 files.

Expected image: `OneROM/build-1541hud/1541HUD_OneROM_T0.0.18_v0.7.2_LiveMotorLog.uf2`.

The branch-only workflow compiles the passive base firmware, T0.0.18 user plugin, and preserved USB plugin, but does not itself produce a flashable UF2. A green workflow is necessary, not a substitute for completing the local BIN/UF2 build and hash check.

## Hardware test

1. Confirm T0.0.17 is recoverable. Flash only the new, locally built T0.0.18 UF2 to the dedicated UB4 monitor.
2. Power-cycle the drive; read a directory to confirm normal 1541 operation.
3. Open the CDC port in PuTTY. Verify `LIVE MOTOR=0` when idle and `LIVE MOTOR=1` while the spindle runs. Compare with `MOTOR state=0/1` on transitions. A native sample may lag by up to one second; do not require every short pulse to appear.
4. Close PuTTY, open the existing Reconnect Test 02 GUI, and verify track, motor, head, density, WP, RPM, SYNC and sector telemetry during the cycle program. Confirm reconnect position recovers after a GUI disconnect.
5. Leave the drive running for several minutes and watch for missing telemetry, unusual log flood, drive lockup or red fault LED. Stop and return to the T0.0.17 UF2 if any passive-monitor or drive behavior regresses.

Record the build SHA256 hashes and the exact pass/fail observations before considering any merge into `dev-1541hud`.
